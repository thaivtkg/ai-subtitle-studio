# 1. Purpose

C5 turns the already completed Help Center + Guided Tour runtime into a production-ready **Getting Started** experience.

C5 owns:

- production tutorial content;
- the minimal production semantic-anchor bootstrap needed by that content;
- one local production DEMO asset generated by the closed C4 capture pipeline;
- automated acceptance for the production content path;
- manual production-path acceptance;
- Windows/PyInstaller release smoke acceptance.

C5 does **not** redesign the Guided Tour engine.

The core invariant remains:

> `TourEngine` is an already-closed consumer of immutable tutorial definitions. C5 supplies production content and production composition wiring; it does not bend engine behavior to make content work.

# 4. C5 product strategy

The production guide is a **safe, non-destructive orientation tour**.

It MUST NOT:

- create a Project;
- open an OS file picker;
- import real media;
- load Whisper or another model;
- require CUDA;
- start transcription/generation;
- write subtitles;
- export a file;
- mutate `ProjectState`;
- invoke a Worker merely for demonstration;
- depend on network access;
- require user media;
- use synthetic mouse forwarding;
- use pixel coordinates;
- depend on a raw Qt signal name in JSON.

Allowed runtime effects are limited to:

```text
semantic navigation
spotlight/callout presentation
one real user CLICK on the Video Workspace navigation button
local DEMO media playback
Tour progress persistence owned by the existing TourEngine/first-run flow
```

# 5. Minimal Production Anchor Contract v1 — LOCKED

C5 exposes exactly six semantic production anchors.

| Semantic ID | Production QWidget | Registration | Consumer step | Policy |
|---|---|---|---|---|
| `dashboard.root` | `self.page_dashboard` | `register` | `dashboard_overview` | `FALLBACK_TO_INFO` |
| `dashboard.new_project` | `self.btn_new_project` | `register` | `create_project_entry` | `FALLBACK_TO_INFO` |
| `navigation.video_workspace` | `self.nav_btns[1]` | `register` | `open_video_workspace` | `REQUIRED` + `CLICK` |
| `workspace.subtitle_editor` | `self.sub_editor` | `register` | `subtitle_editor_overview` | `FALLBACK_TO_INFO` |
| `workspace.ai_generation` | `self.generation_panel` | `register` | `ai_workspace_overview` | `FALLBACK_TO_INFO` |
| `export_center.root` | `self.page_export` | `register` | `export_center_overview` | `FALLBACK_TO_INFO` |

No other production semantic ID is part of C5 v1.

Legacy/example IDs from earlier design documents such as:

```text
media.new_from_url
workspace.video
workspace.timeline
generate.start
context.editor
export.softsub
export.hardsub
```

MUST NOT be revived merely because they appeared in earlier examples.

## 5.1. Registration API

Production composition code MUST call only:

```python
AnchorRegistry.register(semantic_id, widget)
```

C5 MUST NOT author a production `register_resolver(...)` binding.

The current `AnchorRegistry.register()` implementation internally delegates through a weak reference. That internal implementation detail is allowed and does not change the C5 contract: C5 composition code uses the static `register` API only.

## 5.2. New Project attribute promotion

The existing local variable:

```python
btn_new_project = self.create_side_action_button(...)
```

MUST become a stable MainWindow composition reference:

```python
self.btn_new_project = self.create_side_action_button(...)
```

This promotion MUST NOT change:

- button text;
- style;
- signal wiring;
- project-creation behavior;
- UI hierarchy;
- business services.

Its purpose is only to make the existing production widget addressable by a stable semantic anchor.

## 5.3. Bootstrap placement

`ui/Gui.py` owns one private composition method:

```text
_register_tour_anchors()
```

Required bootstrap order:

```text
all six target widgets constructed
        ↓
self.tour_anchor_registry = AnchorRegistry()
        ↓
self._register_tour_anchors()
        ↓
InteractionObserver / Spotlight / TourEngine wiring
        ↓
first possible tour start
```

The method MAY:

- register the six locked IDs;
- reference existing MainWindow widget attributes.

The method MUST NOT:

- create widgets;
- navigate;
- start a Tour;
- inspect tutorial JSON;
- contain per-step state;
- mutate Project/application business state;
- query widgets by display text;
- use `findChild()` as a semantic lookup mechanism;
- use object order or pixel coordinates;
- create a second anchor registry.

# 6. Production Getting Started guide identity

Production file:

```text
resources/tutorials/getting_started.json
```

The existing production file is a one-step placeholder with:

```text
guide_id = getting_started
content_version = 1
```

C5 replaces the learning content with a nine-step production tour.

Therefore C5 MUST use:

```text
guide_id = getting_started
content_version = 2
```

Rationale:

- `guide_id` is the stable semantic identity and MUST NOT change.
- The learning experience changes materially from one Welcome step to nine production steps.
- `TourProgressStore.status()` reports an older stored content version as `OUTDATED`.
- Reusing `content_version = 1` could incorrectly treat completion of the old Welcome-only guide as completion of the new tour.

C5 does not change first-run policy. Existing C2 behavior remains authoritative: first-run banner presentation is only for `NOT_STARTED`; an `OUTDATED` record is not silently converted to first-run onboarding.

# 7. Production tour — normative nine-step contract

The exact step order is:

```text
welcome
→ dashboard_overview
→ create_project_entry
→ open_video_workspace
→ subtitle_editor_overview
→ ai_workspace_overview
→ generation_demo
→ export_center_overview
→ finish
```

| # | Step ID | Type | Surface | Anchor | Policy / interaction |
|---|---|---|---|---|---|
| 1 | `welcome` | INFO | `dashboard` | — | — |
| 2 | `dashboard_overview` | INFO | `dashboard` | `dashboard.root` | `FALLBACK_TO_INFO` |
| 3 | `create_project_entry` | INFO | `dashboard` | `dashboard.new_project` | `FALLBACK_TO_INFO` |
| 4 | `open_video_workspace` | ACTION | `dashboard` | `navigation.video_workspace` | `REQUIRED` + `CLICK` |
| 5 | `subtitle_editor_overview` | INFO | `workspace` | `workspace.subtitle_editor` | `FALLBACK_TO_INFO` |
| 6 | `ai_workspace_overview` | INFO | `workspace/generate` | `workspace.ai_generation` | `FALLBACK_TO_INFO` |
| 7 | `generation_demo` | DEMO | `workspace/generate` | — | local GIF |
| 8 | `export_center_overview` | INFO | `export_center` | `export_center.root` | `FALLBACK_TO_INFO` |
| 9 | `finish` | INFO | inherit current `export_center` | — | — |

## 7.1. Step 4 is the only ACTION

`open_video_workspace` MUST be the only `ACTION` in Getting Started v2.

It MUST use:

```json
"anchor": "navigation.video_workspace",
"target_policy": "REQUIRED",
"interaction": { "kind": "CLICK" }
```

The Tour observes the real user click; it MUST NOT invoke `click()` on behalf of the user.

The production navigation button continues to perform its normal application behavior after the observer sees the mouse release.

## 7.2. Post-ACTION backward fence

Step 4 has:

```text
allow_back = false
```

Step 5 also has:

```text
allow_back = false
```

This is intentional. It prevents Back from immediately re-entering the ACTION step and forcing the user to click Video Workspace a second time.

From Step 6 onward, Back is allowed again where safe.

## 7.3. Step 8 navigation

`export_center_overview` is an INFO step with:

```json
"surface": { "route": "export_center" }
```

Therefore navigation is system-driven by the existing `TourEngine → NavigationAdapter` path.

This does not perform an export and does not invoke export business logic.

## 7.4. Step 9 surface inheritance

`finish` intentionally omits `surface`.

The engine therefore keeps the current Export Center surface and shows the final information callout without another navigation request.

# 9. Preconditions policy

C5 Getting Started v2 has:

```text
guide preconditions = []
step preconditions  = [] for all nine steps
```

This is both a product decision and a compatibility decision.

Source finding at the C5 base commit:

- guide-level preconditions are checked by `TourEngine.start()`;
- step-level preconditions are parsed into `TourStep.preconditions` but are not consumed by `_process_current_step()`.

C5 therefore MUST NOT rely on step-level preconditions and MUST NOT modify `TourEngine` to add that behavior.

The production tour is deliberately designed so it requires no Project, media or background-job state.

# 10. DEMO media contract

C5 Step 7 consumes:

```text
resources/tutorials/assets/getting_started_generation.gif
```

The JSON path MUST remain relative:

```text
assets/getting_started_generation.gif
```

`TourCatalog` resolves it against the tutorial resource root and confines it to the `assets/` subtree.

## 10.1. Runtime media type

The current `DemoMediaViewer` accepts exactly:

```text
image
gif
```

Therefore C5 MUST use:

```json
"media_type": "gif"
```

It MUST NOT use the older design-document labels:

```text
IMAGE
ANIMATED_IMAGE
```

This is a source-contract alignment, not a C3 redesign.

## 10.2. Fit compatibility

`DemoSpec.fit` is accepted by the parser, but the current `DemoMediaViewer` does not consume the `fit` value when rendering.

C5 MUST therefore not depend on `fit` for correctness.

The production GIF MUST be authored at a 16:9 aspect ratio so the current 480×270 demo presentation does not require runtime aspect-ratio correction.

C5 still writes:

```json
"fit": "contain"
```

because it is the existing schema field/default and preserves future-compatible intent without requiring a C3 change.

# 11. C4 production capture scenario

C4 pipeline implementation stays closed.

C5 only supplies the first production scenario to the currently empty developer registry.

Required scenario identity:

```text
scenario_id = getting_started_generation
output      = getting_started_generation.gif
mode        = ISOLATED
```

The scenario MUST use only the six locked production semantic anchors.

It MUST NOT introduce a capture-only production anchor such as:

```text
generate.start
workspace.generate_button
```

## 11.1. Scenario behavior

The C5 v1 scenario is intentionally a safe visual orientation of the workspace/generation context, not a fake transcription run.

Normative intent:

```text
construct isolated MainWindow
→ verify navigation.video_workspace is visible
→ hold initial state briefly
→ ClickAction("navigation.video_workspace")
→ WaitSettledAction()
→ hold workspace state long enough to capture an animated result
→ encode GIF
```

No Project/service operation is required.

The scenario SHOULD use `CaptureScope.FULL_WINDOW` so capture does not depend on a target that is hidden on the initial Dashboard frame.

Recommended profile:

```text
window_size = (960, 540)
fps = 10
output_scale = 1.0
default_wait_timeout_ms = 3000
```

The exact Hold durations may be tuned during TDD only to achieve a clear deterministic GIF while staying within C4 validation limits. They are capture-authoring values, not product runtime semantics.

## 11.2. No NavigateAction in C5 v1

At the C5 base commit, `IsolatedAppFactory` supplies `MainWindow` to `CaptureNavigationAdapter`, while that adapter requires either:

```text
callable router
or
router.navigate_to_route(...)
```

The production MainWindow does not expose the latter contract.

C5 MUST therefore avoid `NavigateAction` rather than patch C4 navigation solely for this asset.

Semantic `ClickAction("navigation.video_workspace")` already exercises the real production navigation button and stays within the locked six-anchor contract.

## 11.3. Asset validation limits

The committed GIF MUST satisfy existing `TutorialAssetValidator` policy, including:

```text
width  <= 1600
height <= 1200
pixels <= 1,920,000
size   <= 8 MiB
frames = 2..200
duration <= 20 seconds
```

CI validates committed assets; CI MUST NOT regenerate them.

# 13. Missing-target behavior

Exactly one C5 anchor is `REQUIRED`:

```text
navigation.video_workspace
```

Reason:

- it is the target of the only ACTION step;
- without it the engine cannot observe the required user interaction.

If unresolved after settle timeout:

```text
TourState → RECOVERING
Retry / Skip Step / End Tour remain available through existing engine behavior
```

The other five production anchors use `FALLBACK_TO_INFO`:

```text
dashboard.root
dashboard.new_project
workspace.subtitle_editor
workspace.ai_generation
export_center.root
```

If one is unavailable:

```text
spotlight target is dropped
callout remains visible
Next remains available
Tour continues safely
```

C5 MUST NOT convert orientation targets to `REQUIRED` merely to make screenshots/tests stricter.

# 14. Zero-mutation contract

Starting and completing Getting Started v2 MUST NOT cause business-state mutation except the existing tutorial progress record.

During the nine-step path, C5 MUST NOT call:

```text
ProjectService create/open/save methods
MediaImportService import/download methods
Whisper/model loading
generation Worker start
export execution
Recovery write/restore operations
```

Allowed state changes:

```text
UI route/tab/drawer selection
Guided Tour presentation state
Tour progress DISMISSED/COMPLETED persistence through existing C2/C1 behavior
```

The real click on `navigation.video_workspace` is a UI navigation action, not a business-data mutation.

C5 implementation MUST be TDD-driven.

The implementation plan may refine test file names, but the following contracts are mandatory.

Automated test MUST load the real production catalog and assert:

```text

content_version == 2
len(steps) == 9
exact step order
exact step types
exact surfaces/subroutes
exact six semantic anchor references
only open_video_workspace is ACTION

root preconditions empty

finish surface is None
```

The test MUST parse through the real `TourCatalog`/`TourParser`, not duplicate the parser with a hand-written JSON assertion only.

## 15.2. Production anchor bootstrap test

An isolated real `MainWindow` with mocked business dependencies MUST prove that the six locked IDs are actually registered to the intended widgets.

Tests MUST use the existing `AnchorRegistry` API and production navigation/visibility state.

Required evidence:

```text
Dashboard state:
  dashboard.root resolves
  dashboard.new_project resolves
  navigation.video_workspace resolves

Workspace state:
  workspace.subtitle_editor resolves

Workspace/generate state:
  workspace.ai_generation resolves

Export Center state:
  export_center.root resolves
```

The test MUST NOT accept display-text lookup as proof of registration.

## 15.3. ACTION production-path test

A production-path UI test MUST prove:

```text
start Getting Started
→ reach open_video_workspace
→ engine enters WAITING_ACTION
→ real user-style CLICK on navigation.video_workspace
→ observer does not consume the event
→ production page navigation still occurs
→ engine advances to subtitle_editor_overview
```

No synthetic Tour-owned business command is allowed.

## 15.4. Zero-mutation integration test

Using strict mocks/spies for the injected production services, automated acceptance MUST prove that traversing the safe tour path does not create/import/generate/export user data.

Navigation/UI calls are allowed; business service calls listed in Section 14 are not.

## 15.5. C4 asset contract

Automated acceptance MUST prove:

```text
_get_registry().ids()
→ contains exactly getting_started_generation for the C5 production registry

python -m tools.demo_capture list
→ reports Listing 1 scenarios...

python -m tools.demo_capture validate
→ PASS with committed production GIF
```

The registry-ID assertion belongs in an automated test. C5 MUST NOT change the closed C4 `list` command merely to make it print scenario IDs.

The existing CI asset-validation command remains authoritative and MUST stay generation-free.

## 15.6. Regression suite

Before C5 manual acceptance:

```text
python -m unittest discover -s tests -v
python -m compileall core ui workers tools tests
python -m tools.demo_capture validate
```

All must pass.

# 18. Source-contract mismatches explicitly accepted by C5

C5 records the following current-source facts instead of hiding them.

## M1 — Legacy DEMO media labels differ from current C3 runtime

Earlier design text referred to:

```text
IMAGE
ANIMATED_IMAGE
```

Current C3 viewer accepts:

```text
image
gif
```

**C5 resolution:** use `gif` in production JSON. No C3 change.

## M2 — `DemoSpec.fit` is not consumed by current viewer

Parser/model accept `fit`, but current viewer does not branch on it.

**C5 resolution:** author the GIF at 16:9 and retain `fit: contain` as declarative intent. No C3 change.

## M3 — Step preconditions are parsed but not executed by TourEngine

`TourStep.preconditions` exists, but the current engine only gates Tour start on guide-level preconditions.

**C5 resolution:** Getting Started v2 uses no guide or step preconditions. No TourEngine change.

## M4 — C4 production registry is empty

Current `tools.demo_capture.cli._get_registry()` returns an empty registry.

**C5 resolution:** register one production `getting_started_generation` scenario as C5 content/config. C4 runner/validator/encoder remain unchanged.

## M5 — Current isolated capture navigation wiring is not compatible with `NavigateAction`

C4 `CaptureNavigationAdapter` expects a callable router or `navigate_to_route()`, while current isolated wiring supplies MainWindow directly.

**C5 resolution:** the production scenario uses semantic `ClickAction("navigation.video_workspace")` and does not modify C4 navigation.

None of M1–M5 is permission to silently change C1–C4 architecture.
